# BelowTrace 居民完整旅程与内容底稿

> 状态：产品内容底稿，尚未用于 PPT。  
> 核验日期：2026-09-20。  
> 原则：只把官方资料或本产品明确标记的历史数据当作事实；不把地图命中、311 记录或现场口头说法包装成法律结论、故障结论或资助资格。

## 1. 我们真正要解决的问题

地下室返水发生时，居民面对的不是单一的“找水管工”问题，而是四条时间不同、规则不同的线同时出现：

1. **人身安全**：眼前的积水、污水与电器可能让人不敢进入地下室。
2. **报备与证据**：DWSD 的损害索赔要求先取得 Service Request（SR）号码，并在发现返水后 45 天内提交书面索赔。
3. **责任判断**：市政收集系统与房屋内、私有地块内的排水和私有 sewer lateral 不是同一责任范围；原因未知时不能先替任何一方下结论。
4. **修复与资助**：居民既可能要处理紧急清理，也可能需要做检查、申请项目、等审批、配合施工和验收。

BelowTrace 的职责不是替政府、保险公司、工程师或律师作决定。它应当在每一个时点告诉居民：**现在先保证什么、已经知道什么、还不知道什么、下一步可验证的动作是什么，以及哪些截止日期和材料不能丢。**

## 2. 对现有流程的审查结论

另一个 AI 提出的五个问题里，方向基本对，但有两处必须改正：

| 判断 | 结论 | 需要怎样处理 |
| --- | --- | --- |
| DWSD 没接电话就把人锁死 | **成立，但不是完全看不到信息。**现在仍会显示 Case File 和部分地址/地下数据；真正被锁住的是后续的行动与项目匹配。 | 报备状态必须继续如实保留，但“了解我的地址与选项”必须始终可走。 |
| 地理情报埋得深 | **成立。**地址命中后的项目覆盖、历史记录、附近工程等，尚未在最需要安定感的第一屏变成清楚的行动信息。 | 地址输入后立刻出“地址事实卡”，并把它和行动流程并列。 |
| 外勤会口头甩锅 | **问题成立，表述不可采纳。**没有可靠证据可以把这归因成普遍行为，也不能让产品教用户对抗工作人员。 | 改成中性的“把现场沟通变成可追溯记录”：记录日期、姓名/单位（如对方主动提供）、SR 号、对方陈述、是否给出后续步骤；请求确认记录与下一步。 |
| 申请后断头 | **成立。**当前的“关闭案件”在项目申请、补件、排期、施工和验收之前就出现，错误地把“发现项目”当成“问题解决”。 | 建立本地案件跟踪，直到居民选择“工作完成”或“停止跟踪”。 |
| 首 30 分钟没有安全分流 | **成立，且优先级最高。**当前只有泛化的手套、拍照提示，不能应对带电积水这种最危险场景。 | 在任何行政步骤前放入来源明确的安全分流；不要自行给出断电、燃气设备或封堵管道的操作指令。 |

以下叙述目前没有充分官方依据，不能放进产品、演示或对外材料：

- “DWSD 通常等 40 分钟、暴雨周末无法接通”；
- “外勤人员最擅长口头推诿”；
- “PSRP 补件固定只有 5 天”。

它们可以成为用户访谈中要验证的假设，不能作为事实或产品文案。

## 3. 新的产品骨架：并行两条线，而不是四步闸门

原来的线性流程把“先成功报备”变成一扇门。居民真实的旅程应改为一个一直可见的案件主页：

```text
发生返水
  ├─ A. 现在是否安全？        （始终置顶）
  ├─ B. 我的地址已知什么？    （输入地址即刻可见）
  └─ C. 我现在该做什么？
       ├─ 报告给 DWSD / 记录 SR
       ├─ 确认现场发现与原因状态
       ├─ 索赔、检查、项目申请可并行推进
       └─ 跟踪补件、排期、施工、验收，直至完成
```

这不是放松报备要求。对于 DWSD 的损害索赔，SR 号码依然是官方要求；只是等待报备成功时，居民不再失去安全指导、地址事实和准备材料的知情权。

## 4. 居民端的完整内容与状态

### 0. 任何页面顶部：先做安全分流

标题：**“先确认这里是否安全进入”**

内容只使用可核验的低风险指导：

- 如果积水区域有配电箱、电器、插座或电线，**不要走入积水**。这是 DWSD 明确发布的提示。
- 如有即时人身危险或火灾紧急情况，拨打 911；不要让 BelowTrace 判断电气、燃气或建筑安全。
- 在安全、干燥的位置拍摄照片和视频；记录发现日期和时间。
- 保留清理、临时住宿、检查和修复的收据。它们可能与索赔或项目审查有关。

按钮：`我现在处于安全位置，继续处理案件`  
辅助入口：`查看 DWSD 官方安全提示`、`我需要紧急帮助`

不应出现的内容：自行拉总闸、触碰电器、堵住下水口、操作燃气设备等具体操作教学。官方资料不足或专业风险过高时，产品必须提示联系相应的紧急服务或持证专业人员。

### 1. 地址事实卡：不等电话、不承诺资格

标题：**“这份是你家地址的记录，不是资格决定或故障结论。”**

输入地址后立即展示四个区块，每一个都要有来源、数据日期和“这不代表什么”的说明：

1. **项目初筛**
   - `地址位于 PSRP 指定社区范围内` / `未命中当前范围` / `数据无法确认`。
   - 若命中：`这让你值得进一步核验；仍须满足收入、1–4 户住宅、与 2021 年灾害关联、非重复补助等官方条件。`
   - 若未命中：`不表示没有其他帮助或索赔权利，只表示本项当前社区边界未命中。`
2. **地址与附近基础设施记录**
   - 后巷/附近是否有公开的排水工程记录，距离与数据日期。
   - `工程在附近不证明它造成返水；它只是提出问题时可核对的公开背景。`
3. **历史请求与环境记录**
   - 同一区域的历史 311/公开请求数量、FEMA 等公开图层（如有）。
   - `历史记录不说明这一次的原因，也不代表每一条记录对应一户居民。`
4. **今天带走的材料清单**
   - 地址、发现时间、照片、收据、SR 号码（若已有）、联系人和文件链接。

固定按钮：`开始/继续报备`、`先准备我的索赔与项目材料`、`查看数据来源`。

### 2. DWSD 报备：记录“尝试”与“已报备”，绝不虚构成功

标题：**“报告返水，取得 SR 号码”**

文案：DWSD 官方要求在发现返水后联系 DWSD 或使用 Improve Detroit；若要提交损害索赔，必须先取得 SR 号码。DWSD 电话为 `(313) 267-8000`，并以应用内来源卡和最后核验日期为准。

两个并列状态：

- `我已取得 SR 号码`：输入 SR、报告日期/时间、渠道；进入“等待/确认现场发现”。
- `我尝试了但尚未取得 SR`：保存尝试时间和渠道；页面不锁死，案件主页仍显示地址事实、照片清单、索赔倒计时和项目准备。

可选提示：`也可在 Improve Detroit 报告；请把得到的编号保存在这里。` 不得显示“已经报备”，除非居民输入编号或明确确认。

### 3. 现场沟通与原因：从“谁有错”改为“我们已有哪类证据”

标题：**“把现场沟通记下来；原因仍可保持未知。”**

居民不应被迫在“市里的问题”或“我自己的问题”中二选一。表单应分别记录：

- DWSD 是否到场：`已到场 / 尚未到场 / 不知道`；
- 这次沟通的日期、时间、SR；
- 对方给出的原因描述（可照原话记录，非必填）；
- 是否收到书面或可查询的结果：`有 / 没有 / 不知道`；
- 对方明确说过的下一步（若有）。

安全、中性的话术：

> “请告诉我这次服务请求的编号，以及系统中记录的描述和下一步。如果现场结果可以查询或有书面记录，请告诉我应该通过哪个官方渠道确认。”

页面的结论仅能是以下状态之一：

- `公共系统问题已有官方记录`：显示损害索赔和材料清单；
- `私有侧问题已有检查证据`：显示持证水管工/CCTV 检查与项目初筛；
- `原因未确认`：并列显示“等待/跟进官方结果”和“如需检查，寻找持证专业人员做 CCTV”，不预先归责。

### 4. 两条正式路径可并行：索赔与修复/项目

#### A. 损害索赔

标题：**“保住 45 天窗口，并准备能核对的材料。”**

官方规则：发现返水后 45 天内提交书面 Notice of Claim；提交前需要 DWSD SR 号码。

案件卡应展示：

- `发现日期`、`截至日期`、`剩余天数`；
- `SR 号码`、`索赔是否已提交`、`提交编号/日期`；
- 材料清单：清楚照片、受损物品/金额、清理/水管工等收据、至少两份维修或更换估算（DWSD 的索赔表要求这些材料）；
- `索赔正在审查，并不等于 DWSD 已承认责任或一定付款。`

#### B. 私有管线检查、修复与 PSRP

标题：**“先区分紧急止损、检查、项目申请与正式施工。”**

PSRP 卡只在地址初筛命中时突出显示，但应允许所有居民查看官方条件。正确文案：

- 当前政策规定：符合条件的业主可获得 grant，向符合条件住户出租的业主可获得 forgivable loan；每户资助最高通常为 `$40,000`，个案例外由城市决定。
- 初筛命中**不是批准**。必须继续核对低于 HUD 80% AMI、1–4 单元住宅、与 2021-06-25/26 灾害关联、社区范围、不在 floodplain、无重复补助等要求。
- `在签署非紧急私人维修合同前，先向官方项目入口确认该工作会不会影响你的申请、可报销范围或重复补助判断。`
- 如用户确有迫切安全/卫生需要，产品不应阻止其求助；只提示保留书面估价、发票、照片与许可资料，并向项目方核实。

### 5. 从“申请”到“真的完成”：本地案件跟踪器

标题：**“申请不是结束；这是你的等待与施工记录。”**

每条索赔、检查、PSRP 申请或修复都有独立状态：

`未开始 → 已提交 → 等待回复 → 需要补充材料 → 已批准/未批准 → 等待排期 → 施工中 → 验收/完成`

每一个状态提供四个字段：

- 编号与官方联系人；
- 最近一次动作和日期；
- 下一件要做的事；
- 截止日期（**只由用户填入通知中的日期，或由来源明确的官方规则预填**）。

补件卡应显示：`这是你从官方通知中抄录的截止日期，请以通知原文为准。` 不能写死“5 天”。

“关闭案件”只应在居民选择 `修复完成` 或 `我不再希望跟踪` 时出现，并明确：`关闭只删除/停止本浏览器中的提醒，不代表索赔、项目或维修已经完成。` 最好保留 `重新打开`。

## 5. 必须落地的数据规则

1. **三层措辞。**
   - 记录：`数据表显示 / 地图命中 / 公开工程记录`；
   - 推断：`值得核验 / 可能相关，但不能据此判断原因`；
   - 决定：`只有 DWSD、项目审查、持证专业人员或正式文件能决定`。
2. **每张关键卡都要有来源、版本/日期、适用范围。**例如 PSRP 的 97 社区名单与条件、工程数据的更新时间、311 记录的时间范围。
3. **地址范围与个人资格分开。**不显示“你可获得 $40,000”；显示“该地址命中项目社区范围，最高额度和最终资格由官方审查”。
4. **记录先于叙事。**系统应保存用户自己填写的日期、编号、照片、收据清单与通知截止日；不要替用户生成不真实的报备或现场结论。
5. **默认本地保存，清楚说明。**目前没有经居民同意的云端案件管理能力，就不能暗示市政府、项目方或团队会收到这些资料。

## 6. 实施优先级：先做哪一块

### P0：本次比赛演示必须呈现

1. 在 Case 首页加安全卡，引用 DWSD 官方安全提示。
2. 让“查看我的地址事实与项目初筛”在未取得 SR 时也可进入；保留“尝试报备”的真实状态。
3. 地址事实卡明确展示：PSRP 社区命中、附近公开工程/历史记录、数据日期、以及“不等于资格/原因”。
4. 去掉或改写所有在申请前出现的“修好，结案”按钮。
5. 用一个示例地址演示“电话尚未接通但居民仍得到安全、证据、项目初筛和下一步”的完整价值。

### P1：让它从比赛 Demo 变成可用工具

1. 把 Step 2 改成“现场沟通与证据记录”。
2. 建立索赔、检查、项目申请的本地状态跟踪和用户录入截止日。
3. 每份动态政策卡加入来源、最后核验日期、失效提醒和官方链接。
4. 补足地址数据的覆盖、更新时间与缺失数据处理；任何无法精确地理匹配的地址，显示“不确定”而不是猜测。

### P2：用真实试点验证，而不是用想象填空

在没有真实访谈前，优先验证以下五个问题：

1. 用户是否能在一分钟内判断“我能不能安全进入地下室”？
2. 电话未接通时，地址事实卡是否降低焦虑、提高下一步完成率？
3. 用户是否理解“项目社区命中”与“最终资格”不同？
4. 用户是否能完整记录 SR、发现日期、材料和实际补件期限？
5. 从申请到施工期间，什么提醒和渠道最容易让人放弃？

访谈对象应包括经历过返水的居民、社区组织/住房辅导者、持证水管工或项目服务人员。访谈前不假设他们会“甩锅”，只问事实：他们收到了什么记录、在哪一步卡住、什么资料最难取得。

## 7. 对外叙事的最终一句话

**BelowTrace 不是把居民推过一个报修表单；它把地下室返水发生后的安全、地址事实、证据、索赔和长期修复放进同一份可核对的案件记录，让人在最混乱的第一小时也不会做出不可逆的错误。**
